分支命名规矩

分支名意思
main / master主干 = 这个仓库的正式版本。main 和 master 意思一样，只是仓库建的时期不同
workbench/xxx工作台实验分支。一个分支一件事，名字里写着干嘛的（比如 workbench/slack-fix-v2 = 溢出松弛修复第二版）
backup/xxx备份快照，别在上面改东西
release/xxx、publish/xxx发布用分支

改代码的标准动线（补丁流）

  1. 从主干拉一个 workbench 分支
  2. 改动写成 补丁文件（patches/000X-名字.patch），默认不生效——想试的时候用 token 打开
  3. 推上去，CI（自动质检机器人）自动跑编译+测试
  4. bench（A/B 测试）里加一个"臂"，和基准同种子对跑
  5. 出判词：转正 / 中性 / 判死 / 留观

为什么这样：主干永远干净，每个改动自带开关和证据，随时可退。这叫"补丁即证据单元"。

CI 是什么，红了怎么办

CI = GitHub Actions 自动质检。每次推代码它自动：编译 → 跑测试 → 跑 bench。绿=过，红=有问题。

铁律：推送后必查 CI，红了必须修到绿再交付。

已知例外：libtests 有 4 个上游基线红（上游本来就红，我们不背不藏，写在明处）。

动手前检查清单

  • ☐ 这个仓库是赛马娘相关仓库吗？是的话，先问主人要不要动（有许可规则）
  • ☐ 改动是不是默认关闭、不影响现有行为？
  • ☐ 有没有引入魔法数字（没出处的裸数字）？有就消灭或标来源
  • ☐ 提交信息写清楚改了什么、为什么
