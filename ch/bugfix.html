🐛 修 Bug 维护语义

复现、种子、世界线——抓虫子的纪律，和一次丢 2798 个文件的惨痛教训。

修 bug 五步

  1. 先复现，再谈修：复现不了就先解决复现，别猜
  2. 固定种子：用固定种子把问题局面录下来，可以一遍遍重放（这叫固定世界线）
  3. 最小化：把触发条件削到最少
  4. 写补丁、默认关：修复也要走补丁流，带开关
  5. 回归验证：修完跑一遍 bench，确认没伤及无辜（分数大盘不能无故掉）

复现难怎么办

真实案例：之前有个局面，CI 里迭代了三次才复现出来。复现难 ≠ 不能修，而是：① 把复现过程本身固化成种子+脚本，写进 CI；② 复现脚本就是修复的验收标准。复现脚本丢了，修复就等于没做。

2798 个文件失踪案（必读教训）

案情：泳装青云天空一局完整育成的抓包数据（465 对请求响应，2798 个文件），当年用 API 一个个传到了 GitHub，但只建了 blob、从没提交进任何分支的 tree。这种文件叫"悬空 blob"，GitHub 约两周自动回收。2026-08-16 审计发现时已无力回天。

教训：

  • 上传 ≠ 保存。提交进分支、能在文件页看到，才算保存
  • 大批量文件归档，传完立即验证：文件数、总字节、抽查内容三件套
  • 不可替代的原始数据（抓包、dump）至少存两处：GitHub + 云盘/手机

现状：索引和公式闭环书还在（见 hlpatch-observation-architecture），源文件还在手机上（/data/user/0/jp.co.cygames.umamusume/files/hlpatch-observations），想恢复就用 hlpatch 重新导出。

验证铁律

  • 大文件交付前必须全量内容校验——只验结构不验内容等于没验
  • 改策略打分类代码，旧基准分数作废重跑，不拿旧分数比
  • 禁止未验证的全量批量修改：跨多处的替换必须逐个验证再合并
